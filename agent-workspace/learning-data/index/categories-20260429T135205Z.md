## Adversarial caveats

**1. Sample window bias toward S13 wire-in smoke events.**
The 100-event tail is the most recent 100 events, which includes the S13 failure_mode wire-in smoke tests (`s13-smoke-1`, `s13-smoke-2`, `s13-smoke-3`). Both non-null failure_mode events are synthetic. The 2.0% failure_mode population rate reflects smoke coverage, not natural failure rate. Natural failure rate in this sample is 0/100. This is the single most important distortion in this run.

**2. Multi-session criterion for promotion includes smoke sessions — over-counting breadth.**
Bash and Edit both appear in smoke sessions (`s13-smoke-1` and `s13-smoke-2`), inflating their apparent session diversity. Bash: 3 "sessions" but one is a synthetic smoke session. Edit: 3 "sessions" but one is `s13-smoke-2` with an injected reject. If smoke sessions are excluded from the session-count, Bash and Edit drop to 2 sessions (still qualifying), but the margin is thinner. Consider tightening to ≥3 non-smoke sessions for robust promotion signal.

**3. `failure_mode=B` and `failure_mode=H` are both first-ever non-null events — no calibration history.**
This is the first corpus with populated failure_mode. The 2 non-null events cannot establish a rate baseline; they only confirm the wire-in fires. A meaningful failure rate requires ≥10 natural (non-smoke) failure events. The 2.0% rate should be treated as "instrumentation confirmed, rate unknown" not as "2% of tool calls fail."

**4. `TaskCreate` promotion promoted on tokens_real=0 for all 13 events — token cost is invisible.**
All 13 TaskCreate events in the promotion-candidate bucket show `tokens_real=0`. This is structurally different from Bash (max 9262) or Read (max 28438). Either TaskCreate genuinely costs zero tokens (it's a harness-side write with no LLM inference) or token tracking does not capture its cost. If the latter, the promotion-candidate token column is misleading for TaskCreate and any downstream cost-analysis using this field will undercount.

**5. 5 uncategorized events are all from a single session — any Grep/ToolSearch failure would be invisible.**
With Grep and ToolSearch each appearing in one session only, a systematic failure of these components in one session would remain uncategorized (no multi-session pattern to trigger drift detection). The corpus needs ≥2 natural sessions with these components before the classification system can surface their failures.
