## IMPL-tier decisions made (per D-003 § Open Questions doctrine)

### IMPL-S12-1: Research-scanner output path = `dogfood/<TS>.md` not `dogfood/<picked-tool>.md`

**Discovery**: D-005 § 5.5d.3 prose says output goes to `dogfood/<picked-tool>.md`. But the research-scanner methodology produces a SURVEY of multiple candidates BEFORE picking — naming the file after the picked tool means the file name encodes the conclusion, which: (a) prevents writing the file until the conclusion is reached (artificial sequencing); (b) hides what was rejected from filename-only inspection; (c) confuses two artifacts (survey-report ≠ dogfood-insight) into one path.

**Decision**: split into TWO artifacts.
- Survey report: `dogfood/agent-pick-1-research-report-<TS>.md` — what the research-scanner produces (multi-candidate; conclusion at top, evidence below).
- Dogfood insight: `dogfood/<picked-tool>.md` — what the dogfood loop produces (single-tool focused; what we LEARN from the picked tool to apply to stockforge).

**Rationale**: matches DSPy's own discipline of separating evaluation (multi-input) from compilation (focused improvement). Each artifact has one job. Filename inspection of `dogfood/` directory shows both the survey log AND the conclusions over time as separate files; future `dogfood/langgraph.md` (hypothetical) would sit alongside `dogfood/dspy.md` cleanly.

**Trade-off accepted**: 1 extra file in `learning-data/dogfood/` per dogfood cycle (vs prose's implied 1 file). For 6-month projection of ~6-12 dogfood cycles, +6-12 files is negligible vs filename-clarity gain.

**D-005 amendment carry-over**: surface in S15 (Track 7) D-005 amendment alongside IMPL-S11-2 path-resolution carry-over. Append-only.

### IMPL-S12-2: research-scanner.md tools = read-only set (no Bash, no Write)

**Discovery**: research-scanner's job is to fetch external content (READMEs + commits via WebFetch) and produce a report. Two tooling options were evaluated: (A) include Bash for `git ls-remote` style SHA lookups; (B) WebFetch-only.

**Decision**: WebFetch-only. Tools list = `[Read, Glob, Grep, WebFetch]`. No Bash. No Edit. No Write (the dispatched agent itself writes via its general-purpose Write inheritance, but the SUBAGENT TEMPLATE only declares the read-research surface).

**Rationale**: minimum risk surface. Bash in research-scanner adds clone/install/exec attack-surface that is irrelevant to the read-only research role. WebFetch is purpose-fit. (The dispatched general-purpose agent inherits its full `*` toolset — but our research-scanner.md declares the methodology, not the tool grants; declaring the read-only surface enforces the discipline at the methodology level even when the actual dispatch model has broader access.)

**Trade-off accepted**: agent must use github.com URLs (`raw.githubusercontent.com/.../HEAD/README.md` + `api.github.com/repos/.../commits`) rather than git protocol. Slightly less SHA-precision (HEAD ≠ specific tag), but more portable + Phase-0 friendly + no auth needed.

### IMPL-S12-3: Capability-map task class addition = vocabulary only, no strength row

**Discovery**: D-005 § 5.5d.3 success criterion #4 mentioned "capability-map.md += possibly +1 task_class cell (e.g., `tool-survey`)". Capability-map's own promotion rules say: "Single-occurrence observations → DO NOT add to map (one-off, may not generalize)" but ALSO "Map gap → propose entry: if task_class is novel, add tentative entry post-execution + flag `provisional: true`".

**Decision**: append `tool-survey` to vocabulary list (line ~50) WITH `_(provisional, S12 first instance)_` flag. Do NOT add a strength row in the table (waits for ≥3 instances per promotion threshold).

**Rationale**: vocabulary expansion is permitted on novel observation per Heuristic #3; row addition (strengths/limits table) requires ≥3 instances per "Update Protocol" line. Splitting the rules respects both: vocabulary captures the new concept's existence; row-data waits for evidence of generalizability.
