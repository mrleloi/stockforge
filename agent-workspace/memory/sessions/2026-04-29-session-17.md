### IMPL-S17-2: weight lookup from weights.yaml vs caller-passes-delta

**Discovery**: initial sync-tracker-update.sh signature required CLI arg `<delta>` from caller. This violates the "tunable weights" contract (edit weights.yaml once → all callers pick up new values).

**Decision**: refactor signature to `<override_delta>` optional CLI arg; default behavior is `weight_<event_type>` lookup from weights.yaml. Override mode preserved for testing/non-standard partial-credit events.

**Trade-off**: caller cannot easily compute custom delta (must edit weights.yaml or pass override). Acceptable: standard event types are the common case.

**Documented**: this session log + sync-tracker-update.sh header docstring + sync-pull SKILL.md "Inputs" section.

## Lessons learned (1 candidate; L-S17-1)

### L-S17-1: Spec storage-substrate fields (e.g., "SQLite") are IMPL-tier when bash+POSIX portability is binding

**Rule**: when an upstream decision (D-NNN) names a specific storage technology (SQLite / Postgres / Redis / specific DB) but Phase 0 portability rules (L-S11-1: bash + POSIX only) constrain hook environment, the storage substrate is IMPL-tier per D-003 § Open Questions doctrine. Agent picks the bash-portable substrate; documents deviation in a downstream IMPL-tier decision; defers migration to the phase when target tech ships.

**Reason**: spec authors typically lock the functional contract (categories / weights / thresholds / events / tiers) but use convenient shorthand for storage ("SQLite"). The functional contract is binding; the storage shorthand is implementation detail subject to environment constraints.

**How to apply**:
- Pre-flight verify the named tech is available (`command -v <tool>`).
- If unavailable AND L-S11-1 binds: pick portable substrate; ship MVP.
- Document deviation in NEW IMPL-tier decision (D-NNN); cite source decision (D-MMM § ...) + portability constraint (L-NN-N) + deferred-migration plan.
- Original spec stands as Phase 1+ migration target; no upstream REV needed.

**Anti-example**: blindly invoking python+sqlite3 from `scripts/hooks/*.sh` because spec said "SQLite" — adds 1 NEW L-S11-1 violation on top of 5 pre-existing; deepens portability debt without forward-progress benefit.

**Correct example (this session)**: D-006 § Decision + § Why + § Risks documents IMPL-S17-1 deviation; Phase 1+ migration captured as Open Question; D-002 spec retained verbatim.

**Promotion candidate**: amend `proposals/decision-discipline.md` § "IMPL-tier resolution doctrine" with a Rule 3 sub-clause covering storage-substrate-vs-portability-binding pattern. S18+ candidate after Track 8b lands.
