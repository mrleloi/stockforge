## Lessons codified

### L-S80-1: gawk regex `\$` source-vs-pattern semantics — empirical verification mandatory

**Rule**: Before changing any awk regex literal involving `\$` or `\\$` or `\\\\$`, empirically verify behavior against representative input via `awk '...'/regex/' { print }' /tmp/test.txt`. Do NOT assume gawk follows POSIX ERE semantics literally — gawk 5.3.2 emits "warning: escape sequence \$' treated as plain $'" but actual matching behavior is context-dependent.

**Why**: S80 T2 debug spent ~10K main tokens chasing a regex bug that didn't exist. Empirical test `awk '/\\$/ { print }'` on file with `has-bs \` line correctly matched it (literal `\` at EOL). Source `/\\$/` (2 backslashes) compiles to regex pattern matching "literal `\` at end-of-line" per POSIX ERE — my intuition that gawk treats `\\$` as `\$ → literal $` was wrong in this gawk build.

**How to apply**: When debugging awk regex behavior or adding new patterns containing `\` or `$`:
1. First write minimal repro: `printf 'line\\\n' | awk '/your-pattern/ { print "match" }'`
2. Verify match/no-match against known input WITHOUT changing the production regex
3. Only modify production regex AFTER confirming actual gawk behavior matches your intent
4. Beware: gawk lint warning "escape sequence X treated as plain Y" may be misleading — empirically test outcome

**Anti-pattern recognition**: Changing a working regex based on intuition without empirical re-test. Cost: ~10K tokens of debug + wasted carry-line "fix" + revert cycle in S80.

### L-S80-2: `grep -c ... || echo 0` produces multi-line capture; breaks awk `-v` numeric coercion

**Rule**: When extracting a count via `grep -c ...` for use as a boolean/integer flag, do NOT use the `|| echo 0` fallback pattern. Instead use `if grep -q ...; then VAR=1; else VAR=0; fi` for clean integer output.

**Why**: `grep -c` outputs count + newline AND exits 1 when match-count is 0. The `|| echo 0` then fires AFTER the 0 already printed, producing TWO lines: `0\n0\n`. After `$()` command-substitution strips ONLY trailing newline, the captured value is `0\n0` (with embedded newline). When passed to awk via `-v var=...`, awk's lazy string-to-number coercion fails: `var == 0` may evaluate FALSE because string `0\n0` doesn't match canonical `0` representation.

**How to apply**: Audit any `grep -c ... 2>/dev/null || echo 0` pattern in scripts that subsequently use the value with awk numeric comparison or `[ -gt ]` integer test. Refactor to:
```bash
if grep -qE 'PATTERN' "$f" 2>/dev/null; then VAR=1; else VAR=0; fi
```
This produces clean `0` or `1` always.

**Anti-pattern recognition**: `VAR="$(grep -c PATTERN file 2>/dev/null || echo 0)"` followed by `awk -v var="$VAR"` then `var == N` test. Easy to miss because the same code works correctly when grep finds at least 1 match (single integer output from grep, no `|| echo 0` fallback needed).

**Backlog candidate**: Add Pattern F to `bash-hook-lint.sh` Check 10 — detect `grep -c ... || echo 0` in non-conditional position (i.e. value used in awk `-v` or arithmetic).
