## Lessons learned (3 candidates)

### L-S14-1: Progressive-disclosure refactor first-draft tends to 150–180 LOC; budget compression reserve

**Rule**: When extracting from a 200–280 LOC content-heavy skill into SKILL.md + references/*.md, plan SKILL.md at ≤140 LOC target (10 LOC under ceiling) with verbatim references absorbing 150–230 LOC. The reason: the "decision rules + when-to-use + anti-patterns" core content has natural floor ~110 LOC; once you add validation pre-conditions + smoke test + see-also you're at 130–140; first-draft slips to 160–180 if you keep an example block in SKILL.md instead of moving to references. Verify with `wc -l` after every Write; recompress on overshoot before considering the refactor done.

**Severity**: medium (ceiling-creep risk; would catch at Stop hook anyway; costs an extra Edit pass).
**Auto-detect**: yes — already covered by drift-signals D1.
**Promotion candidate**: `write-a-skill` SKILL.md best-practice section, or new `try-n-approaches` skill body amendment at Track 6 wrap-up.

### L-S14-2: Skill-vs-command duplication is a refactor multiplier

**Rule**: When a `.claude/commands/<name>.md` and a `.claude/skills/<name>/SKILL.md` exist for the same procedure (e.g., `spec-to-wiki`, possibly others), they almost always have ~80% content overlap. The command should be a thin invoker (≤120 LOC: when-to-use + input + 1-line steps + see-also pointing to skill); the skill holds the load-bearing procedure. Refactor the command first (cheap); skill refactor is a separate task. Don't try to bundle if scope-tight — deferring 1 violation is cheaper than half-finished bundles.

**Severity**: low (process discipline; not a bug).
**Auto-detect**: partial — drift-detector D1 catches both as separate violations; no special signal needed for the duplication itself.
**Promotion candidate**: `write-a-skill` SKILL.md "skill vs command" section, or new charter clause in `architecture.md` § Slash command vs skill responsibility split (Track 7).

### L-S14-3: settings.local.json wildcard preserves deny precedence; doesn't supersede charter

**Rule**: User-requested loose permissions (e.g., "wildcard * for the project") should write to `.claude/settings.local.json` (project-scoped, user-specific, gitignored) rather than the team-wide `.claude/settings.json`. Per Claude Code permission resolution, **deny rules from any source take precedence over allow rules from any source**. Therefore wildcard `Read(**) / Edit(**) / Write(**) / Bash(*)` in local settings does NOT bypass the team-wide deny on `PROJECT_CHARTER.md`, `agent-workspace/constitution/**`, etc. — it just stops prompting on the wide majority of routine paths.

**Severity**: medium (governance correctness; ensures charter immutability invariant survives loose-permissions request).
**Auto-detect**: partial — `update-config` skill encodes the read-existing-merge-carefully discipline; no automated check for "deny rules still cover charter paths" yet.
**Promotion candidate**: amendment to `harness-bootstrap-permission-override` memory entry OR new bullet in `update-config` skill's preconditions checklist.
