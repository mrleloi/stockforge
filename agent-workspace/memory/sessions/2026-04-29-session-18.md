## IMPL-tier decisions made (S18)

### IMPL-S18-1: library-only L1 — no claude-CLI subprocess invocation in Phase 0

**Discovery**: D-002 REV-2 § A spec'd L1 prompt port from `extract-l1.ts:33-64` but the source TS file at lines 100+ contains claude-CLI subprocess dispatch + multi-agent session-file discovery (qwen / codex / companion / gemini paths). Subprocess invocation conflicts with: (a) Phase 0 deterministic-substrate-first principle; (b) Charter Principle 9 "no LLM math" (LLM only interprets); (c) brittleness on bash hook environments where claude binary may not be PATH-available.

**Decision**: ship `build_extraction_prompt` + `parse_llm_response` + `extract_messages_from_jsonl` (windowing) as a library only. Caller (Phase 1+ Anthropic SDK client or claude-CLI bridge) composes dispatch on top. Phase 0 module is callable + smoke-testable today via fixture; no external CLI dependency.

**Trade-off**: L1 extraction not auto-fired in Phase 0; Phase 1+ wire-in still needed (logged as carry-over to S19+).

**Documented**: D-007 § Decision + § Why + Open Questions.

### IMPL-S18-2: TranscriptCache — full re-parse on grow vs incremental merge (Phase 0 simplification)

**Discovery**: source `transcript-cache.js` implements full incremental merge for token-extraction (parses bytes from `cached.bytesRead` to `stat.size`, merges per-model token counters into cached state). Porting that mechanic for the parameterized parser callable adds ~80 LOC complexity for a marginal gain (single extra full-file read on append events; for 10K-line transcripts this is microseconds).

**Decision**: Phase 0 simplification — on grow/shrink/rewrite, do full re-parse. Cache-hit on identical mtime+size still avoids the read entirely (the dominant access pattern). Token-extraction-style incremental merge can be re-added later if profiling justifies; meanwhile the API surface stays simple.

**Trade-off**: marginally higher I/O on rapid append-mode workloads; mitigated by mtime+size cache-hit being unaffected.

**Documented**: this session log + transcript_cache.py module docstring.

## Lessons learned (1 candidate; L-S18-1)

### L-S18-1: Cross-language regex porting requires explicit FAILURE_PATTERNS extension per identity locale

**Rule**: when porting language-specific keyword regex from a source repo (TS / JS / Python / Go), do not assume the source's locale set covers the target project's identity. claude-sessions origin patterns were RU + EN (Son Nguyen / Andrey Bursukov authorship). Stockforge identity is VN-primary (per project memory + Charter "Vietnamese stock market"). Every imported keyword-regex tier must be audited for target-locale gaps and explicitly extended with target-locale phrases before shipping.

**Reason**: missing target-locale patterns silently degrade extraction quality. Vietnamese failure phrases ("không hoạt động", "thất bại", etc.) are fingerprints stockforge cares about — not catching them in L0 means downstream calibration data is biased toward EN-only sessions, even when the actual session is Vietnamese.

**How to apply**:
- Pre-flight when porting: identify all keyword/phrase regex tiers (FAILURE_PATTERNS, NEXT_STEP_PATTERNS, ERROR_RE, etc.).
- Audit each tier against project identity locale (VN for stockforge; en/vi as multi-locale for international projects).
- Extend each tier with N target-locale phrases before shipping; cover via test cases (one per phrase minimum).
- Document the locale extension in the port-decision file (D-NNN) so it shows up in drift/sandwich-verifier review.

**Anti-example**: copying extract-l0.ts FAILURE_PATTERNS verbatim to Python without adding VN — drops 5 phrases of stockforge identity coverage; only EN/RU sessions register failures.

**Correct example (this session)**: D-007 § Decision explicitly cites the 5 VN phrases as part of the decision; tests `test_extract_failures_vietnamese_*` cover each individually.

**Promotion candidate**: amend `proposals/architecture-amendment.md` § "When porting from source repos" with a Rule N "audit + extend identity-locale-specific regex tiers before ship" sub-clause. Or extend `evidence-extraction/SKILL.md` with a "Cross-locale port checklist" section. S19+ candidate after Track 6 secondary or Track 9 ships.
