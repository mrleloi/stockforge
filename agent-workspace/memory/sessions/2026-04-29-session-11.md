## IMPL-tier decisions made (per D-003 § Open Questions doctrine)

### IMPL-S11-1: Indexer choice — bash + node-eval (NOT sqlite3)

**Pre-flight discovery**: `command -v sqlite3` → not found on Windows Git Bash (current dev environment).

**D-005 § Open Questions** explicitly listed this as IMPL-tier: "Final RAG index choice: SQLite FTS5 Phase 0 vs DuckDB FTS vs simple bash grep+regex — IMPL-tier; agent picks at S11".

**Decision**: pick "simple bash + node-eval" branch.

**Rationale**:
- Zero new dependencies (bash + node already used in component-telemetry.sh; pattern proven S8/S10).
- Cheap-first ordering doctrine — minimum viable indexer for current scale (<100 events/day).
- Pluggable: index/ files are JSON + NDJSON; Phase 1+ swap to FTS5 (when sqlite3 ships with deployment image) or pgvector (when DB infra arrives) is a hook-script rewrite, not a data-layout migration.
- Honest about boundary: index produces deterministic file-level metadata (manifest) + sample dump (NDJSON copy) — no LLM-driven indexing.

**Trade-off accepted**: full-text query is via `grep` rather than indexed FTS5 query — slower for large corpora, but corpus is currently 60 events. Re-evaluate at next S11 promotion (event volume signal).

## Lessons learned (potential agent-notes promotions)

### L-S11-1: sqlite3 unavailable on Windows Git Bash → bash+node fallback for Phase 0 indexers

**Context**: Index-rebuild hook design required portable indexer. sqlite3 CLI not in Windows Git Bash by default. SQLite FTS5 was D-005's preferred Phase 0 choice but un-deployable.

**Rule**: Phase 0 hooks running on dev machines must NOT assume sqlite3 / DuckDB / external CLIs beyond bash + node + standard POSIX (find, grep, wc, mv, rm, cat, stat, sort, tail). When richer indexing needed → defer to Phase 1+ where deployment ships pgvector/sqlite3 in Docker image.

**Severity**: low (informational; design constraint only).

**Promotion**: candidate for `agent-workspace/constitution/financial-data-protocol.md` § Phase boundaries — "Phase 0 portability: bash + node + POSIX only". Surface in S15 (Track 7) constitution port.

### L-S11-2: Spec drafting bugs surface at IMPL time → IMPL agent resolves, surfaces amendment

**Context**: D-005 § 5.5d.2 deliverables prose put `categories-<TS>.md` under `agent-workspace/memory/learning-data/index/` while §5.5d.1 deliverables put `index/` as subdir of `agent-workspace/learning-data/`. S10 implementation went with §5.5d.1; permissions + README aligned with §5.5d.1.

**Rule**: When IMPL agent finds spec internal inconsistency at execution time → resolve in favor of the layout that downstream artifacts (permissions, README, gitkeep) are already aligned with; document IMPL-tier decision in session log; surface for spec amendment at next planning boundary (do not block ship).

**Severity**: medium (recurring spec-drafting risk; Spec-as-source butterfly = drift signal D4 territory).

**Promotion**: candidate `IMPL-tier-resolution-doctrine` skill, OR amendment to `agent-workspace/constitution/decision-discipline.md` § "When spec inconsistency surfaces at IMPL time" (Track 7 S15).
